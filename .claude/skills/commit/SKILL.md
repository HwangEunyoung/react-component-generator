# commit: 변경사항 분석 후 컨벤션 커밋

현재 작업 디렉토리의 git 저장소에서 변경사항을 분석해 논리적 단위로 나누고, 컨벤션에 맞는 한국어 커밋 메시지를 작성해 자동으로 커밋한다. 사용자 승인을 기다리지 않는다(단, 시크릿 의심 파일이 있는 경우는 예외로 확인을 받는다).

## 워크플로우

### Step 1: 저장소 지침 확인

저장소 루트의 `AGENTS.md`(없으면 `CLAUDE.md`)에 커밋 메시지 컨벤션이 명시되어 있으면 그것을 우선 따른다. 없으면 이 스킬의 기본 규칙(Step 4)을 따른다.

### Step 2: 변경사항 분석

- `git status`로 변경/미추적 파일 목록을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)로 실제 변경 내용을 확인한다.
- `git log --oneline -10`으로 기존 커밋 메시지 스타일이 있으면 참고한다(레포에 커밋 이력이 없으면 생략).

### Step 3: 논리적 단위로 분류

변경사항을 하나의 목적을 가진 단위로 묶는다.

- 기능 추가, 버그 수정, 리팩터링, 설정/문서 변경처럼 목적이 다르면 원칙적으로 분리한다.
- 단, 서로 강하게 연관되어 분리하면 빌드가 깨지는 경우(예: 함수 시그니처 변경 + 호출부 수정)는 하나의 커밋으로 묶는다.
- 무관한 여러 목적이 섞여 있으면 파일 단위로 나눠 여러 커밋을 제안한다.

### Step 4: 커밋 메시지 작성 (한국어)

형식: `type: 요약`

- `feat`: 새로운 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변경 없는 코드 구조 개선
- `chore`: 빌드/설정/의존성 등 잡무성 변경
- `docs`: 문서 변경만 있는 경우
- `test`: 테스트 코드 추가/수정
- `style`: 포맷팅 등 코드 의미에 영향 없는 변경

요약은 한 줄, 간결하게 작성하고 "무엇을 바꿨는지"보다 "왜 바꿨는지"에 집중한다. 변경 이유나 배경 설명이 필요하면 빈 줄 뒤에 본문을 덧붙인다.

### Step 5: 자동 커밋 (승인 절차 없음)

1. `.env`, credentials, 키/토큰 파일 등 시크릿으로 보이는 파일이 스테이징 대상에 있으면, 이 파일만은 예외적으로 커밋을 멈추고 사용자에게 포함 여부를 확인받는다. 나머지 단위는 계속 진행한다.
2. 시크릿 의심이 없는 커밋 단위는 승인 없이 바로 진행한다. 커밋 단위에 포함할 파일만 명시적으로 `git add`한 뒤 커밋한다.
3. 여러 단위로 나눴다면 계획된 순서대로 하나씩 자동으로 커밋한다.
4. 세션에 별도의 attribution(Co-Authored-By 등) 지침이 있으면 커밋 메시지 말미에 포함한다.
5. 모든 커밋이 끝나면 `git log --oneline`으로 생성된 커밋 목록과 `git status`로 남은 변경사항을 확인해 사용자에게 결과를 보고한다.

## 안전 규칙

- 커밋 자체는 사용자 승인 없이 자동으로 진행한다. 단, 시크릿 의심 파일은 예외로 항상 확인받는다.
- `git add -A`, `git add .` 사용을 금지하고, 커밋 단위에 포함할 파일을 명시적으로 지정해 스테이징한다.
- `--no-verify`, `--amend` 등은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- push는 하지 않는다. 커밋까지만 자동으로 수행하고, push는 사용자가 별도로 요청할 때만 진행한다.
