> **RIGID RULE — 상황에 맞게 변형하지 마라.**
> 아래 절차를 생략하거나, 순서를 바꾸거나, "이번만 예외로" 처리하지 않는다.

## 0. 프로젝트별 규칙 우선 조항

이 파일은 **기본값(fallback)** 이다. 프로젝트 루트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그 규칙이 이 파일보다 우선한다.** 충돌 시 이 파일의 해당 조항은 무시하고 프로젝트 규칙을 따른다. 프로젝트 규칙이 없는 항목만 이 파일의 기본값을 적용한다.

## 1. 적용 기준

### 반드시 TDD 적용

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API 엔드포인트/핸들러** (요청 검증, 응답 형식, 에러 처리)
- **유틸리티 함수** (순수 함수, 데이터 변환, 파서)
- **버그 수정** (재현하는 실패 테스트 없이는 수정 코드를 작성하지 않는다)

### TDD 불필요

- **타입 정의** (interface, type alias — 컴파일러가 검증)
- **설정 파일** (`vite.config.ts`, `tsconfig.json`, `eslint.config.js` 등)
- **순수 UI 마크업/스타일** (동작 로직이 없는 프레젠테이션 컴포넌트)
- **SQL/마이그레이션 스크립트**

애매한 경우: 실행 시 분기·조건·계산이 있으면 로직으로 간주하고 TDD를 적용한다.

## 2. RED — GREEN — REFACTOR

### RED

- **하나의 동작(behavior) = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트 작성 후 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 다음 단계로 넘어가는 것은 금지.
- 실패 이유는 반드시 **"기능이 아직 구현되지 않음"** 이어야 한다. 문법 오류, import 누락, 타입 에러로 인한 실패는 RED가 아니다 — 먼저 그 오류부터 고친다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드**만 작성한다. **YAGNI** — 지금 요구되지 않는 케이스를 미리 처리하지 않는다.
- 통과 확인은 **신규 테스트 + 기존 테스트 전체**를 대상으로 한다. 신규 테스트만 돌려보고 끝내지 않는다.

### REFACTOR

- 이 단계에서 하는 일: 중복 제거, 이름 개선, 헬퍼 추출.
- 전체 테스트가 **계속 green으로 유지**되는지 매 변경마다 확인한다.
- **새로운 동작을 추가하지 않는다.** 새 동작이 필요하다고 판단되면 REFACTOR를 끝내고 다음 사이클의 RED로 넘어간다.

### 반복

REFACTOR가 끝나면 다음 동작에 대한 **RED로 돌아간다.** 사이클을 건너뛰지 않는다.

## 3. 삭제 강제 규칙

- 테스트보다 프로덕션 코드를 먼저 작성한 것을 발견하면, **해당 코드를 삭제**하고 RED부터 다시 시작한다.
- "일단 참고용으로 남겨둔다", "주석 처리만 해둔다" 는 **금지**. 삭제는 삭제다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트가 불필요하다" | **단순한 코드일수록 테스트 비용이 가장 낮다.** 단순함은 테스트를 생략할 이유가 아니라 테스트를 즉시 끝낼 이유다. |
| "나중에 테스트를 추가하겠다" | **"나중"은 오지 않는다.** 코드가 동작하는 순간 테스트를 쓸 동기가 사라지고, 이후엔 리팩터링 안전망 없이 코드가 굳는다. |
| "시간이 없다" | **RED-GREEN-REFACTOR는 시간을 아끼는 방법이지, 쓰는 방법이 아니다.** 디버깅 없이 바로 동작을 검증하는 쪽이 항상 더 빠르다. |
| "테스트 먼저 쓴 코드를 삭제하면 낭비다" | **순서를 어긴 코드는 검증되지 않은 코드다.** 그 코드가 맞다는 근거가 없으므로 보존할 가치가 없다. |
| "이건 프로토타입이다" | **프로토타입이 오래 산다는 것은 이 바닥의 상식이다.** 프로토타입이라는 이름표는 나중에 검증 없이 프로덕션으로 승격되는 가장 흔한 경로다. |
